# 版本管理

## 正式版本与开发构建

项目采用按发布批次递增的语义化版本，以及按 Git 提交追溯的构建标识。一个正式版本可以包含多次功能、修复和维护提交。日常开发保持根包版本，准备正式发布时统一升级根包、两个 workspace 和锁文件。

正式版本使用 `X.Y.Z`，遵循 [SemVer 2.0.0](https://semver.org/lang/zh-CN/)：

- `patch`：兼容的缺陷修复，例如 `2.0.0 → 2.0.1`。一个 patch 发布可以汇总多次修复提交。
- `minor`：兼容的新功能，例如 `2.0.0 → 2.1.0`，可以同时包含修复。
- `major`：需要使用者调整操作或迁移的不兼容变化，例如 `2.x → 3.0.0`。

兼容性范围包含命令行用法、配置文件与环境变量、安装和服务管理方式、浏览器持久化数据，以及使用者依赖的主要交互。内部重构、测试和文档维护先积累到下一次有实际交付价值的发布。版本级别由整个发布批次的影响决定，提交数量和提交前缀用于辅助整理。

根 `package.json` 是正式版本的来源。`client/package.json`、`server/package.json` 与 `package-lock.json` 保持相同版本，前后端作为一个产品统一交付。

构建标识示例：

```text
v2.0.0 标签上的干净代码             2.0.0                    正式发布
此后任意一次日常提交                2.0.0+dev.gabc1234       开发构建
工作区包含已跟踪或未跟踪的修改       2.0.0+dev.gabc1234.dirty 开发构建
源码缺少 Git 和随包构建信息          2.0.0+unknown           来源未知
```

`gabc1234` 是提交的前七位，完整提交保存在版本详情中。`dirty` 表示构建时包含未提交修改，同一个 dirty 标识可能对应多次本地编辑；正式可追溯交付应从已提交的干净代码构建。`+` 后的内容属于构建元数据，用于识别代码来源；SemVer 比较版本大小时忽略这部分内容。开发构建沿用最近一次正式版本作为基线。

正式发布身份要求当前 HEAD 存在与包版本相同的 `vX.Y.Z` 标签且工作区干净。打包时把身份固化到 `build-info.json`，目标机器直接读取该文件。Git 提交身份和构建时间分别记录，重新构建同一提交只更新构建时间。缺少来源信息时明确显示“来源未知”。

## 日常开发与记录

主线 `main` 保持可构建。需要隔离开发时使用短期分支，功能完成后合回主线。日常提交保持当前正式版本；每个有实际影响的改动同步更新 `CHANGELOG.md` 的“未发布”，按新增、改进、修复、维护分类，用使用者能理解的变化描述结果。同一功能的多次调整合并成一条记录。

```text
多次开发提交 → 未发布变更持续积累 → 确定发布范围
                                  ↓
                      统一更新版本、归档变更与检查
                                  ↓
                          发布提交 → 版本标签 → Release
```

`CHANGELOG.md` 是面向使用者与维护者的持续版本总览；`docs/releases/vX.Y.Z.md` 与远端 Release 正文面向第三方使用者，只列他们新增可用的能力、具体操作改善和可见问题修复。条目使用界面、操作及结果描述变化，同一功能的相关修改合并。独立 Markdown 文档保留版本一级标题，上传正文时去掉该标题，GitHub 页面直接在自身版本标题下显示变更列表；审阅时结合实际 Release 页面检查排版。回归测试、测试覆盖率、内部重构、协议适配、构建工具和发布流程维护等开发工作记入提交记录，Release 仅保留其对使用者的具体影响。

安装、环境要求、配置、使用、升级和迁移说明统一维护在 README 或部署文档，测试报告、校验步骤、附件介绍和发布过程维护在开发或版本文档。

修订发布说明时同步仓库文件与远端正文；已经发布的标签、变更记录和附件保持固定，后续功能与修复进入新的发布批次。

## 准备和发布

1. 审阅未发布条目，按整个批次的兼容性影响选择版本。
2. 执行 `npm run version:prepare -- patch`、`minor`、`major` 或明确的 `X.Y.Z`。命令同步包版本和锁文件，归档未发布条目并保留空的未发布区域，生成 `docs/releases/vX.Y.Z.md`，更新 README 和部署文档的当前下载版本。该命令只修改文件。
3. 按第三方使用者视角审阅发布说明，每条交代新增可用能力、具体操作改善或可见问题修复，合并同一功能的相关修改并保留提交链接；开发工作留在提交记录，发布概述、使用教程和验证报告移入对应文档。将 `GITHUB_REF_NAME` 设为本次标签执行 `npm run check`，覆盖 GitHub Actions 的标签环境，完成发布提交。
4. 在干净的发布提交上创建与根包版本相符的附注标签，执行 `npm run release:check`，再推送发布提交与标签。GitHub Actions 复核版本、来源和文档，执行完整检查，然后将 npm 包及 SHA-256 文件上传到同版本草稿。配置了定时时间的版本在附件验证后保持草稿，由定时工作流到期公开；其他版本完整上传后直接发布。
5. 核对 Actions、Release 附件和下载链接，按部署文档验证校验和与全局安装。紧急修复沿用相同流程，可以只包含一项修复。

以实际选定的版本替换以下命令中的 `X.Y.Z`：

```bash
npm run version:prepare -- X.Y.Z
GITHUB_REF_NAME=vX.Y.Z npm run check
# 审阅并提交发布准备后的文件，然后执行：
git tag -a vX.Y.Z -m "Codex Web vX.Y.Z"
npm run release:check
git push origin main vX.Y.Z
```

发布准备命令会拒绝倒退版本、新版本的重复标签或空的未发布内容。再次传入当前已准备的明确版本时，命令保留包版本、变更记录和已审阅的发布说明；当前版本尚未创建标签时，继续准备更高版本会报错并提示完成当前版本。`npm run version:check` 已纳入日常检查，校验三个包与锁文件；`npm run release:check` 额外校验干净标签、变更日志、发布说明与当前安装链接。当前自动发布流程接收稳定的 `vX.Y.Z`，开发验证直接使用提交构建；未来需要对外测试版时，再单独引入候选版本及 GitHub 预发布通道。

## 定时发布与正文同步

在推送版本标签前，将目标版本和含时区的 ISO 8601 时间写入 `.github/release-schedule.json`，并随发布准备提交推送到默认分支。例如：

```json
{
  "v2.3.0": "2026-10-29T09:00:00+08:00"
}
```

标签工作流执行完整检查、草稿创建、两个附件上传、下载校验和及临时全局安装验证，然后保持草稿。`Publish scheduled releases` 工作流被调用时读取计划，到期后重新验证草稿附件和安装来源，再公开已有草稿；提前调用返回 `pending` 并退出。检查失败时保留草稿，后续执行沿用原版本重试；正式发布后仅检查附件完整性，保持已交付附件固定。两个工作流共用 `release-publish` 并发组并启用多任务排队，避免草稿上传与公开同时执行，也防止后续检查替换排队中的发布。

定时发布由独立的持久调度任务在目标时间主动调用上述工作流，GitHub cron 提供补偿检查。仓库的 cron 表达式请求每五分钟触发一次，[GitHub 实际调度可能延迟或缺失](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)；发布时间配置是公开前的时间检查条件。持久调度任务由维护者在已授权的常驻主机上建立，随具体发布任务登记和验证。Linux 主机优先使用用户级 [systemd timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)，配置明确时区的 `OnCalendar` 和 `Persistent=true`，核对触发精度、退出登录后的运行条件、失败重试及结果日志。任务使用已有授权主动触发工作流，并在触发后持续查询运行和 Release 状态；凭据及调用命令须在相同的非交互执行环境中验证，代码使用隔离检出或固定脚本。

```text
持久定时任务到期 ─┐
                  ├→ 发布工作流 → 检查时间及附件 → 公开原版本草稿
GitHub cron 补偿 ─┘                                      ↓
                                            核对发布时间、下载及安装
```

交付定时任务时记录目标版本、含时区时间及 UTC 换算、允许延迟、实际任务名称、下次触发时间、重试策略和执行证据。用隔离任务与模拟发布状态验证到期触发、cron 缺席、提前执行、主机恢复后的补执行、重复执行和失败重试。草稿就绪、持久调度任务已建立、正式发布分别报告；公开结果以 `draft=false`、`published_at`、公开附件的 SHA-256 和临时全局安装验证为准。结果检查超过约定完成时限或连续失败时保留失败状态与日志，便于及时处理。

定时工作流需要位于默认分支。手动触发 `Publish scheduled releases` 可以重试到期发布，也会同步发布说明；手动触发继续遵守原发布时间。修改 `docs/releases` 中的说明或发布脚本后，默认分支推送触发正文同步：保留独立 Markdown 文件的标题，只将变更列表写入已有 Release 的正文，保持版本标题、标签和附件固定。

排查漏发时先核对并保存计划、工作流状态、触发记录及日志，区分缺少触发与执行失败。恢复交付时重试已有定时发布任务，继续使用原版本、标签和附件，并分别记录故障原因与恢复后的实际发布时间。

`v2.3.0` 的功能范围为 `v2.2.0..210a695` 的全部 14 个提交，其中 12 个涉及功能和修复，2 个修订已有发布说明；完整记录见[版本比较](https://github.com/hjd-hitsz/codex-web/compare/v2.2.0...210a69577bab649b35cc7d86ef0a8636ac0206fb)。发布准备另行记录版本同步、定时配置和正文排版修复。

## 发布失败与同版本重试

用户指定或确认的版本代表本次交付批次。提交、推送、依赖安装、测试、构建和附件上传失败时，保留同一目标版本，依据日志修复失败环节。只有用户确定新的发布批次时才递增版本。

- 提交或推送失败：保留版本、变更记录和发布说明，解决具体错误后重试原操作。再次执行准备命令时传入明确的原版本 `X.Y.Z`，命令原样保留已准备内容。
- 同一提交遇到网络或服务故障：重跑失败的 GitHub Actions 工作流。`scripts/publish-release.mjs` 复用同版本草稿并重新上传两个附件，上传成功后才将草稿转为正式发布。
- 测试或构建需要修改代码：提交修复并在实际标签环境下重跑完整检查。若标签已推送，先核实该版本从未正式交付，记录远端旧标签对象；将原版本标签更新到修复提交时，以记录的旧值执行 `--force-with-lease`，防止覆盖他人更新。已正式交付的标签与附件保持固定。
- 发布已成功而客户端丢失响应：重试校验正式 Release 的两个附件，保留已交付内容。正式 Release 缺少附件时保留现场并报错，交由维护者核查。

维护者应在 Actions 完成并核对下载附件的 SHA-256、版本来源和临时全局安装结果后，报告发布成功。

## 查看正在使用的版本

- 网页打开“设置 → 关于”，查看网页构建和桥接进程各自的版本、完整提交与可用的构建时间。网页信息在构建时固定，源码桥接信息在进程启动时读取。
- `codex-web --version` 输出便于阅读的标识；`codex-web version --json` 输出完整的 `version`、`displayVersion`、`revision`、`dirty`、`channel` 和 `builtAt`。源码目录可用 `node bin/codex-web.mjs version --json`。
- `curl http://127.0.0.1:8766/healthz` 返回 `ready` 与桥接进程的 `version` 对象。HTTP 200 / 503 继续表示后端连接就绪 / 未就绪。

前端重新构建并刷新后显示新网页标识；桥接版本随进程重启更新。全局命令查看当前磁盘安装包，健康接口查看正在运行的进程。升级排查时同时核对这两个来源。
